# Architecture

How HideLLM is put together, and why the non-obvious parts are the way they are.
Read this before making structural changes.

## The shape of it

```
manifest.json            MV3 declaration: permissions, hotkeys, entry points
src/
  background.js          service worker: the only thing that mutates state
  core/
    ui.js                icons and the three chrome shells (Google / Microsoft / Notion)
    themes.js            the five disguises, built from those shells
    sites.js             per-site hide rules, the base reset, hostname matching
    settings.js          the settings schema, validation and storage
    engine.js            builds the disguise and injects/removes it
  popup/                 the toolbar panel
  options/               the full settings page
icons/                   generated by scripts/make-icons.mjs
test/                    four suites, no framework, no dependencies
scripts/                 icon generation, lint, Web Store packaging
```

`src/core/*` is loaded by three different contexts: the service worker via
`importScripts`, and both HTML pages via `<script>` tags. That's why each module is
an IIFE that hangs its exports off a single `HL` object on whichever global exists
(`self` in the worker, `window` in a page). It's not the fashionable choice; it's
the one that lets the same file run unchanged in all three places *and* be loaded
into a `vm` context by the tests without a bundler.

Load order matters and is the same everywhere: `ui → themes → sites → settings →
engine`.

## What gets injected

Two things, and only after you switch the extension on.

### 1. The stylesheet

Built by `HL.buildCss(site, theme, mode)` from four layers, in this order:

| Layer | Source | Job |
|---|---|---|
| Base reset | `sites.js` → `BASE_CSS` | Flatten every colour, gradient, shadow and blur; hide buttons and icons |
| Typography | `sites.js` → `typographyCss()` | One family, document leading, a page-width column |
| Site rules | `sites.js` → `SITES[site]` | Hide *this* site's shell; optionally its prompts and replies |
| Canvas | `themes.js` → `canvasCss` | Paint the page background: white sheet on a grey desk, or a cell grid |

`buildCss` is pure. The same three arguments always produce a byte-identical
string, and that is load-bearing: `chrome.scripting.removeCSS` only removes a
stylesheet if you hand it the exact text you inserted. So the engine records
`{site, theme, mode}` per tab and rebuilds the string from *that* at removal time.
Recomputing it from current settings would strand the old stylesheet on the page
the moment someone changed themes between apply and remove, which is exactly the
bug this design exists to prevent.

### 2. The toolbar

`chrome.scripting.executeScript` serialises a function to source and runs it in the
page. It closes over nothing, so everything it needs (markup, CSS, height, title,
favicon) arrives as one plain-object argument built by `buildPayload()`.

In the page it:

1. mounts the toolbar markup in a **shadow root**;
2. sets `document.title` and swaps the favicon;
3. watches for the app undoing any of that.

**Why a shadow root.** The base reset flattens every background and colour on the
page with `!important`. The toolbar has to survive that while everything around it
doesn't. Outer stylesheets cannot select into a shadow tree, so the toolbar keeps
its real colours for free. Inherited properties *do* cross the boundary, which is
why the shell CSS opens with `all: initial` and re-declares them.

The host element's own styles are set inline with `!important`, because an inline
`!important` declaration is the one thing the injected stylesheet cannot outrank.

**Why not a screenshot.** The obvious shortcut is a PNG of a real toolbar stretched
to `width: 100vw`. A capture taken at one width and density looks correct only at
that width and density; anywhere else it reads as zoomed-in, which is the single
most obvious tell a disguise can have. Rendering the toolbar in CSS lands it on
exact pixel sizes at any viewport, stays crisp on HiDPI, and needs no bundled
images, which in turn removes the need for `web_accessible_resources`, so a page
cannot fingerprint the extension by probing its asset URLs.

**Why it keeps re-asserting.** These are single-page apps that rewrite the title
and favicon on every route change and occasionally sweep unknown nodes out of
`<html>`. A `MutationObserver` on `<head>` (subtree) and on `<html>`'s direct
children catches that; a 1.5s interval is the backstop for cases the observers
can't see, such as a title set before `<head>` exists. The observers are scoped
narrowly on purpose: a subtree observer on `<html>` would fire on every token
these apps stream in.

## Who owns state

The service worker, exclusively. The popup and the options page read state and post
messages; they never call the scripting API themselves.

That's not ceremony. A popup is destroyed the instant focus leaves it, and an
injection started from a closing popup can be cut halfway: CSS in, tracking record
not written, and now the stylesheet can never be removed cleanly. The worker
outlives the click.

The message API is a flat `{type, ...}` object handled by `HANDLERS` in
`background.js`. Handlers always resolve, returning `{error}` rather than
rejecting, because a rejected `sendMessage` surfaces to the caller as an opaque
runtime error.

## Where things are stored

| Where | Key | What |
|---|---|---|
| `storage.sync` | `settings` | Everything the user chose. Follows the browser profile. Falls back to `storage.local` where sync is unavailable. |
| `storage.local` | `tabState` | `{tabId: {site, theme, mode}}`: what was injected, so it can be removed exactly |
| `storage.local` | `peekTabs` | Tabs currently revealed by a peek |

Nothing lives in module scope: Chrome kills an idle service worker and restarts it
on the next event, so in-memory state is gone whenever it feels like it.

Every read goes through `HL.readSettings()`, which normalises whatever it finds. A
stale key, a theme that no longer exists, or a hand-edited value degrades to a
default instead of throwing: a settings object is not a place to discover you have
an unhandled exception.

`tabState` is read-modify-write, so those updates are serialised through a single
promise chain in `engine.js`. Two tabs finishing their load in the same tick would
otherwise race and lose a record.

## Site matching

`getSiteKey(url)` parses the URL and compares hostnames. It deliberately does
**not** substring match:

```js
url.includes('claude.ai')   // true for https://evil.example/?next=claude.ai
```

That would inject the disguise into an attacker-controlled page. A host is accepted
only if it equals a known host or is a subdomain of one, and anything that isn't
`http:`/`https:` is rejected outright. There are tests for each of those cases.

`HL.matchPatterns()` derives the injectable origins from the same `SITES` table the
runtime uses, and a test asserts it matches `host_permissions` in the manifest,
so the two can't drift.

## Escaping

The document name is user input, and it ends up in the toolbar markup, which is
assigned with `innerHTML`. Every interpolation into that markup goes through
`UI.esc()`, and `settings.js` additionally collapses whitespace and caps the length
at 80 characters. `core.test.js` asserts that a tag-shaped document name comes back
escaped for every theme.

## Tests

```
npm test
```

Four suites, no framework, nothing to install:

| Suite | Covers |
|---|---|
| `core.test.js` | Themes, escaping, hostname matching, the stylesheet builder, settings validation, storage |
| `worker.test.js` | The service worker, driven through real Chrome events: navigation, hotkeys, alarms, messages |
| `ui.test.js` | The popup and options page booted in a stub DOM against a real worker |
| `brand.test.js` | Naming, required documentation, version agreement |

They stub `chrome.*` and load the actual source with `vm.runInContext`, so what's
under test is what ships. What they *don't* do is verify how the CSS renders against
the live sites; that still needs a human with the extension loaded.

The DOM stub in `test/harness.js` deliberately serves only element ids that exist in
the corresponding HTML file. A typo'd `getElementById` then returns `null` and the
page throws, which is the bug we want caught.
